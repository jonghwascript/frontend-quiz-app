# 개요

mi.travels 마크업 작업의 **3단계 — 품질 평가**다.
`/markup_frame` → `/markup`으로 만들어진 결과물을 **Frontend Mentor 솔루션 리포트 체계**에 맞춰 진단하고 점수를 매긴다.

리포트는 두 층으로 구성된다 (Frontend Mentor와 동일한 구조).

| 층 | 내용 | 산출물 |
|---|---|---|
| **1층 · 자동 점검** | 접근성 / HTML / CSS / JavaScript 4개 영역의 규칙 위반 탐지 | 위반 항목 목록 (severity + 파일:라인) |
| **2층 · 코드 리뷰** | 6개 차원의 정성 평가 | 차원별 10점 만점 점수 + 총점 + 등급 |

- 이 커맨드는 **진단만 한다. 코드를 고치지 않는다.** 수정은 사용자가 요청하거나 `/markup`으로 이어서 진행한다.
- 판정은 **반드시 실제 파일을 읽고** 내린다. 추정으로 위반/통과를 적지 않는다. 확인이 안 된 항목은 점수에 반영하지 않고 "미확인"으로 남긴다.

## STEP 0 — 평가 대상 확정 (필수, 항상 먼저 실행)

1. `$ARGUMENTS`로 대상을 정한다.

| 입력 | 대상 |
|---|---|
| 페이지명 (`simple_quote`, `2-1_simple_quote`) | 해당 페이지 + 그 페이지가 `@@include`하는 모든 파일 + 대응 SCSS |
| 파일경로 | 그 파일 하나 (include/컴포넌트 단위 평가) |
| `all` | `static/_markup/html/pages/` 전체 (`sample.html` 제외) |
| 인자 없음 | 대화 맥락상 직전에 작업한 대상. 맥락이 없으면 `all`로 할지 사용자에게 확인 |

2. **평가는 빌드 결과물 기준으로 한다.**
   `static/_markup/html/pages/*.html`은 `@@include`가 남아 있어 그 자체로는 유효한 HTML이 아니다. 문서 구조·중복 ID·헤딩 순서는 include가 합쳐진 뒤에만 정확히 판정된다.
   - `static/{페이지명}.html`(빌드 산출물)이 **소스보다 오래됐거나 없으면** `npm run build`를 실행해 갱신한다.
   - 빌드가 실패하면 그 자체가 **error 1건**이며, 실패 로그를 리포트 맨 위에 싣고 가능한 범위까지만 평가한다.
3. 대상 파일 집합을 확정해 목록으로 만든다.
   - HTML(빌드): `static/{페이지명}.html`
   - HTML(소스): `static/_markup/html/pages/{페이지명}.html` + 그 파일이 include하는 `common/*`, `components/*`
   - SCSS: `static/_markup/scss/pages/_{페이지명}.scss` + 해당 페이지가 쓰는 `components/*`
   - JS: 해당 페이지가 로드하는 `static/js/**` 중 이번 작업에서 만든 것
4. **지적은 소스 파일 기준으로 적는다.** 빌드 결과물에서 발견해도 `static/{페이지명}.html:120`이 아니라 원본인 `static/_markup/html/include/components/simple_quote_form.html:14`로 환산해 표기한다. 환산이 어려우면 양쪽을 병기한다.

> 대상 확정 없이 바로 점검을 시작하지 않는다.

## STEP 1 — 린터 실행 여부 확인 (선택)

Frontend Mentor의 자동 점검은 axe-core / html-validate / stylelint / eslint를 사용한다. 이 프로젝트에는 아직 설치돼 있지 않다.

1. `package.json`의 `devDependencies`와 `node_modules`에 위 도구가 있는지 확인한다.
2. **있으면** 실행해 결과를 STEP 2의 근거로 쓴다.
3. **없으면 임의로 설치하지 않는다.** 사용자에게 한 줄로 묻는다.
   > "html-validate / stylelint / eslint를 설치해 실제 린트를 돌릴까요? 아니면 규칙 기반 수동 점검으로만 진행할까요?"
   - 답이 없거나 수동을 택하면 **STEP 2의 체크리스트를 직접 파일을 읽어 판정**한다. 이때 리포트에 "수동 점검(린터 미실행)"임을 명시한다.
   - 설치를 택하면 devDependency로 추가하고 실행한다. 설정 파일이 없으면 각 도구의 권장 프리셋(`html-validate:recommended`, `stylelint-config-standard-scss`, `eslint:recommended`)을 기준으로 생성한다.

## STEP 2 — 자동 점검 (4개 영역)

각 영역의 위반은 **error / warning / info** 3단계로 분류한다.

- **error** — 동작·접근성·유효성이 실제로 깨지는 것. 반드시 고쳐야 함
- **warning** — 지금 당장 깨지진 않지만 유지보수·호환성 위험
- **info** — 더 나은 방식 제안

### 2-1. 접근성 (axe-core 기준 + 한국어 웹접근성 관례)

| # | 점검 항목 | 기본 severity |
|---|---|---|
| A1 | `<img>`에 `alt` 존재. 장식용 이미지는 `alt=""` | error |
| A2 | `alt`가 파일명·"이미지"·"img" 같은 무의미한 값이 아닌지 | warning |
| A3 | 모든 입력요소(`input`/`select`/`textarea`)가 `<label>`과 연결됨 (`for`/`id` 또는 label 내부 중첩). placeholder는 label 대체가 아님 | error |
| A4 | 헤딩 레벨이 건너뛰지 않음 (h1→h3 금지), 페이지에 h1이 하나 존재 | warning |
| A5 | `<html lang="ko">` 존재 (`common/head.html` 확인) | error |
| A6 | 버튼·링크에 접근 가능한 이름이 있음. 아이콘 전용 버튼은 `.t__hidden` 텍스트 또는 `aria-label` | error |
| A7 | ARIA 속성이 올바른 역할/값으로 쓰였고, 존재하지 않는 id를 `aria-labelledby`/`aria-describedby`로 가리키지 않음 | error |
| A8 | 색상만으로 정보를 전달하지 않음 (에러 상태가 빨간 테두리만이 아니라 텍스트도 동반) | warning |
| A9 | 본문 텍스트 명도대비 4.5:1 이상 (`.c__999`, `.c__aaa` 등 옅은 회색을 본문에 쓰지 않았는지) | warning |
| A10 | 포커스 표시가 `outline:none`으로 제거되고 대체 스타일이 없는지 (SCSS 점검) | error |
| A11 | 클릭 가능한 요소가 `<div>`/`<span>`이 아니라 `<button>`/`<a>`인지 | error |
| A12 | `tabindex`에 0/-1 외의 양수를 쓰지 않았는지 | warning |
| A13 | 터치 타겟이 최소 44×44px 이상인지 (SCSS 수치 확인) | info |
| A14 | 링크 텍스트가 "여기", "더보기"처럼 맥락 없이 모호하지 않은지 | info |

> **자동 점검의 한계를 리포트에 반드시 명시한다.** axe-core류 자동 검사는 전체 접근성 문제의 일부만 잡는다. alt 텍스트가 *적절한지*, 읽기 순서가 논리적인지, 키보드만으로 조작 가능한지, 확대 200%에서 깨지지 않는지는 수동 확인이 필요하다 — 이 4가지를 **"수동 확인 권장" 항목으로 리포트에 고정 출력한다.**

## STEP 2-5 — Design & UX 동작 검증 (필수)

### 검증 원칙

- 소스 검토, 자동 검사, 실제 브라우저 검증 결과를 구분한다. CSS 규칙이 존재한다는 사실만으로 화면에서 정상 동작한다고 판정하지 않는다.
- 각 항목은 **통과 / 실패 / 미확인 / 해당 없음**으로 기록한다. 해당 없음에는 적용되지 않는 이유를 적는다.
- 브라우저 연결 오류, 도구 부재 등으로 실행하지 못한 검사는 **미확인**이다. 소스 점검으로 대체해 통과 처리하지 않는다.
- 기본 화면뿐 아니라 hover, focus, selected, error, reset 상태와 상태 전환을 확인한다.
- 자동 접근성 검사와 별도로 키보드 조작을 확인한다. 실제 스크린리더를 사용하지 않았다면 음성 안내 동작은 미확인으로 남긴다.
- 수정 후 같은 재현 순서로 다시 검사해야 해결로 판정한다. 소스만 수정된 경우에는 **수정 반영 / 재검증 미완료**로 표시한다.
- 같은 원인을 STEP 2와 이 단계에서 발견해도 지적과 감점은 중복하지 않는다. 관련 규칙 ID를 함께 적는다.

### 체크리스트

| ID | 영역 | 확인할 내용 |
|---|---|---|

| UX2 | 선택 표시 | 선택 상태를 배경색·글자색 외에도 테두리, 체크 표시, 텍스트 등으로 구분할 수 있는가 |

| UX9 | 확대·읽기 | 200% 확대에서 내용과 조작 요소를 사용할 수 있는가. 읽기·Tab 순서와 alt 텍스트가 의미에 맞는가 |

### 실행 및 증거 기록

1. 브라우저·뷰포트 크기·확대 배율·빌드 상태를 기록한다. 대표 폭으로 375px, 768px, 1440px을 사용하되 프로젝트 분기점 전후도 확인한다.
2. 초기 화면 → 입력 → 팁 선택 → Custom 전환 → 금액·인원 수정 → 오류 → 정상값 복구 → Reset 순서로 확인한다.
3. 팁 계산기는 Bill 100, People 2, Tip 15%에서 `$7.50` / `$57.50`을 확인하고, People 4로 변경하면 `$3.75` / `$28.75`인지 확인한다.
4. 미완성 입력 상태에서도 Custom과 라디오 선택을 전환하고, 오류 문구가 긴 경우와 큰 결과값에서도 레이아웃을 확인한다.
5. 각 지적에 **재현 순서, 기대 동작, 실제 동작, 소스 파일:라인**을 기록한다. 화면·DOM·로그 중 판단에 필요한 증거를 남긴다. 실행하지 못한 경우에는 소스 근거와 실행 미확인을 명시한다.

## STEP 3 — 코드 리뷰 (6개 차원 채점)

각 차원을 **10점 만점**으로 매기고 3~5줄의 근거를 단다. 근거에는 **실제 파일:라인**을 최소 1개 인용한다.

| 차원 | 카테고리 | 무엇을 보는가 | 적용 조건 |
|---|---|---|---|
| **1. 시맨틱 & 구조** | Code Quality | 문서 구조가 의미를 담는지. 목록은 `ul/li`, 정의형은 `dl/dt/dd`, 폼은 `form`+`fieldset`. div 남발 여부 | 항상 |
| **2. 스타일 아키텍처** | Code Quality | 페이지 전용/공통 분리가 맞는지, 2개 이상 페이지에서 반복되는 스타일이 `pages/`에 갇혀 있지 않은지 | 항상 |
| **3. 파일 구조 / 공통화** | Code Quality | 재사용 가능한 섹션이 include로 빠졌는지, include 파일명이 **용도 기준**인지(페이지명 금지), 반대로 1회성 섹션을 과하게 분리하진 않았는지 | 항상 |
| **4. 접근성** | Design & UX | STEP 2-1 결과를 종합. 자동 검사 통과 여부만이 아니라 **키보드 조작 가능성, 읽기 순서, label 문구의 실질적 유용성**까지 판단 | 항상 |
| **5. 반응형 & 디자인 재현** | Design & UX | `@include media(sm/lg)` 사용, 모바일에서 가로 스크롤 유발 요소 없음, 피그마 값과의 일치도(피그마 URL이 주어졌거나 대화 맥락에 있을 때만) | 항상 (피그마 대조는 자료 있을 때만) |
| **6. 인계 품질** | Documentation | 조건부 노출 TODO 주석이 필요한 자리에 빠짐없이 달렸는지, 주석이 "왜 숨기는지"를 서버 개발자가 알 수 있게 썼는지, 의도적으로 뺀 공통 블록에 이유가 적혔는지 | 항상 |

**적용 제외 처리**: 평가 범위에 해당하지 않는 차원은 **잠금(locked)** 표시하고 총점 계산에서 제외한다. 필요한 검증을 수행하지 못한 경우는 적용 제외가 아니라 **미확인**이다.
- 피그마 자료가 없으면 차원 5의 "디자인 재현" 부분만 잠그고 반응형은 평가한다.
- JS 변경이 없으면 STEP 2-4를 잠근다.
- 이 저장소는 git 저장소가 아니므로 **커밋 품질 차원은 항상 잠금**이다.

### 점수 산정

- **차원 점수**: 10점에서 시작해 차감한다. error 1건당 −1.5, warning 1건당 −0.5, info 1건당 −0.1. 같은 원인이 여러 라인에서 반복되면 **1건으로 묶고 "×N회"로 표기**한다 (같은 실수를 반복했다고 중복 감점하지 않는다). 하한 0점.
- **총점**: 적용 대상의 필수 검증이 완료됐을 때만 잠기지 않은 차원 점수의 **산술 평균**을 소수 첫째 자리로 반올림한다. 평가 범위와 적용 제외 항목을 함께 명시한다.
- **검증 미완료**: 필수 항목에 미확인이 있으면 총점·종합 등급은 **보류**한다. 확인한 소스 영역의 점수는 참고용으로 제시할 수 있지만, 미확인 항목을 뺀 평균을 전체 완성도 점수로 제시하지 않는다. 핵심 기능 error는 점수와 별도로 강조한다.
- **등급 밴드** (Frontend Mentor와 동일):

| 총점 | 등급 |
|---|---|
| 0.0 – 3.9 | Needs Work (보완 필요) |
| 4.0 – 5.9 | Fair (보통) |
| 6.0 – 7.4 | Solid (양호) |
| 7.5 – 8.9 | Great (우수) |
| 9.0 – 10.0 | Exceptional (탁월) |

## STEP 4 — 리포트 출력

아래 형식으로 출력한다. 적용 대상 검증을 완료하고 위반이 0건인 영역만 **"통과"**로 기록한다. 미실행·부분 실행 영역은 **"미확인"** 또는 **"부분 확인"**으로 표시하고 확인 범위와 이유를 적는다.

```
# 마크업 리포트 — {대상}

**총점 8.0 / 10 · Great(우수)**
점검 방식: 수동 점검(린터 미실행) | 빌드: 성공
브라우저 검증: 완료 / 부분 확인 / 미실행 (실제 결과와 환경 기재)
검증 범위: 통과 N / 실패 N / 미확인 N / 해당 없음 N
※ 필수 검증 미완료 시 위 총점 대신 "총점·종합 등급 보류 — Design & UX 검증 미완료"로 표시
대상 파일: 6개 (HTML 3, SCSS 2, JS 0)
```

**출력 규칙**

- 지적 1건 = `severity` + `규칙ID` + `파일:라인` + **왜 문제인지 1줄** + **어떻게 고치는지 1줄(코드 예시)**. 이 4개가 빠지면 지적으로 치지 않는다.
- Design & UX 지적에는 재현 순서·기대 동작·실제 동작을 추가한다. 미확인 항목에는 검증을 막은 원인과 다음 확인 방법을 적는다.
- 소스 점검만 완료했다면 첫머리에 **"소스 점검 완료, Design & UX 검증 미완료"**를 명시한다. 위반을 찾지 못한 것과 검증을 통과한 것을 구분한다.
- "우선 조치"는 **error → warning → info 순, 최대 7개**. 전부 나열하지 말고 실제로 먼저 손봐야 할 것만 추린다.
- "잘한 점"은 빈말이 아니라 **구체적 근거(파일:라인)**가 있을 때만 적는다. 없으면 이 절을 생략한다.
- 리포트 파일로 남길지는 사용자에게 묻는다. 남긴다면 `static/_markup/docs/reports/{대상}_{YYYYMMDD}.md`.
- 자동으로 코드를 수정하지 않는다. 마지막에 한 줄로 안내한다: "수정이 필요하면 항목 번호를 알려주세요. `/markup`으로 이어서 반영합니다."
